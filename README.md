# Ostend

Ostend is a transparency layer for interactions between autonomous software agents and existing HTTP services. It provides a simple, interoperable way for compliant clients to declare when a request was selected, constructed, and submitted autonomously, and for services to observe and record that declaration without changing existing authentication or authorization behavior.

This repository contains the specification, product requirements, and software requirements for Iteration 1 of Ostend (see docs/prd.md and docs/srs.md). The project was initialized using the RAES methodology: https://github.com/aabdullah-bos/raes

## Purpose

Ostend’s goal is to make three dimensions of every request more transparent:

- Identity — Who or what is accountable for the request (preserve existing credential context).
- Capability — What resource or action the request attempts to exercise (observed, not granted).
- Context — Why, when, how, and with what human involvement (Iteration 1 records a narrow declaration of autonomy).

Iteration 1 focuses on a single, well-scoped contextual claim: whether a compliant client declares a request to be autonomous. The intent is observation and discovery, not enforcement or attestation.

## Key principles

- Observation-first: Iteration 1 does not block requests or change upstream authorization decisions. It records voluntary declarations as claims, not proof.
- Minimal and privacy-conscious: Only non-sensitive metadata is emitted by default. Credentials, request/response bodies, prompts, and other sensitive data are not logged.
- Compatibility: Ostend must be deployable in front of existing services without requiring those services to change their authentication model.
- Clear semantics: Declare, classify, and normalize agent-interaction metadata so downstream systems can trust field meanings when the proxy-to-upstream boundary is enforced.

## What Ostend provides (conceptual)

- A concise external declaration clients can send to indicate autonomous request generation and submission.
- Consistent parsing and classification of declarations into one of: valid, missing, invalid, or unsupported.
- Sanitization of caller-supplied reserved fields so downstream metadata cannot be forged.
- Addition of normalized internal metadata that downstream services can consume when they trust the proxy boundary.
- Structured, privacy-conscious observation events per request to support auditing and adoption measurement.
- Health and readiness checks suitable for container platforms.

## Protocol (high level)

Iteration 1 defines a single external request field that compliant clients may include to voluntarily declare autonomy. The proxy classifies each request based on the presence and structure of that declaration; a valid declaration leads to an interaction mode of `autonomous`. All other classifications are operationally treated as `unspecified`.

Classification values:

- valid — Declaration present and conforms to Version 1 profile.
- missing — No declaration supplied.
- invalid — Declaration present but malformed or contains unsupported members/values.
- unsupported — Structurally valid but requests an unsupported profile version.

Ostend exposes normalized internal fields (trusted only behind an enforced network boundary) and emits one structured observation event per completed request describing identity references, attempted operation, declaration classification, upstream outcome, and timing.

## Typical actors and scenarios

- API owner: Deploys Ostend to observe declarations without changing authentication or authorization.
- Service operator: Runs and monitors the proxy; configures a single trusted upstream origin.
- Agent developer: Adds a single request field to declare autonomous operation; no SDK required.
- Downstream application developer and researchers: Consume normalized metadata and structured events to analyze adoption and behavior.

Scenarios include compliant autonomous agents declaring autonomy, existing clients without declarations remaining compatible, malformed or unsupported declarations being observed (not blocked), and downstream services consuming normalized metadata for auditing.

## Scope and non-goals

In Iteration 1 Ostend is explicitly observation-only. It does not:

- Detect or prove a request was generated by an agent.
- Enforce policy or block requests based on declaration values.
- Establish or attest agent identities, sign declarations, or provide cryptographic proof of origin.
- Log credentials, request/response bodies, prompts, or other sensitive data by default.

These non-goals are deliberate to allow safe, incremental learning about how such disclosures behave in real systems.

## Roadmap (high level)

Planned phases include a local prototype, a hosted pilot to validate deployment and observability, and an evaluation phase to gather feedback on declaration semantics, developer experience, and operational behavior. Future directions (post-Iteration 1) may include richer context claims, attestation mechanisms, SDKs, and production deployment models that reduce intermediary trust risk.
