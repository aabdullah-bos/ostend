**Version:** 0.1  
**Date:** July 29, 2026  
**Related document:** Autonomous Agent Disclosure Proxy SRS, Version 0.1.0

## 1. Executive summary

Ostend is a transparency layer for interactions between software agents and existing services.

Its long-term purpose is to make three dimensions of every request visible:

- **Identity:** Who or what is accountable for the request?
- **Capability:** What resource or action is the requester attempting to use?
- **Context:** Under what circumstances is the capability being exercised?

The first iteration focuses on one narrow but foundational contextual fact: whether a compliant client declares that a request was selected, constructed, and submitted autonomously, without a human reviewing and approving that specific operation.

Ostend will initially operate as an observational HTTP proxy in front of an existing service. It will preserve the service's current authentication and authorization behavior, normalize voluntary agent disclosures, and produce structured records that associate the request's existing authenticated identity, attempted operation, and declared interaction context.

Iteration 1 is not intended to stop malicious agents, detect undisclosed automation, prove that declarations are truthful, or make new authorization decisions. Its purpose is to establish a practical vocabulary and integration point for making agent participation more identifiable.

For the proof of concept, Ostend is treated as a trusted, TLS-terminating intermediary and will be deployed as a public proxy on Railway. This deployment protects the client-to-proxy and proxy-to-upstream connections with TLS, but it does not provide end-to-end request integrity against a compromised Ostend deployment. It also relies on the hosting platform for baseline availability protections rather than independently providing comprehensive denial-of-service mitigation.

## 2. Why Ostend

### 2.1 The interaction model is changing

Existing APIs generally assume that a request originates from one of two familiar actors:

- A human operating an application.
- A relatively predictable application acting under a stable service identity.

Agents complicate this model. A request may be generated by software that interprets a broad task, selects intermediate actions, uses multiple tools, and submits operations without a human reviewing each one.

The service may still receive a valid credential belonging to a known user or organization. Authentication can therefore succeed even though the service cannot see whether:

- A human directly initiated the operation.
- A human is observing the operation.
- A human approved that specific operation.
- An autonomous agent selected and submitted it.

### 2.2 Valid authentication does not describe the interaction

Identity remains essential because it establishes provenance and accountability. However, an authenticated identity does not fully describe how its authority is being exercised.

For example, two requests may carry the same valid application credential:

```text
Request A:
A person selected "Download my health report."

Request B:
An autonomous agent decided that downloading the report would help complete
a broader task.
```

Today's service may see these requests as equivalent. Operationally and ethically, they may not be.

### 2.3 Services lack a shared vocabulary

Individual services can invent custom headers, user-agent conventions, or logging fields, but those approaches do not create consistent meaning across clients and services.

A simple interoperable disclosure mechanism creates a starting point for:

- Understanding how autonomous requests appear in real systems.
- Associating agent participation with existing authentication records.
- Developing better audit and observability practices.
- Learning which additional context is useful.
- Building future capability and policy controls from evidence rather than assumptions.

### 2.4 Transparency should precede enforcement

Premature enforcement would require answers that are not yet sufficiently clear:

- Which agent requests should be restricted?
- What proof should be required?
- How should supervision be defined?
- What policies are appropriate for different services?
- How should delegation and task purpose be represented?

Ostend begins by making one fact expressible and observable without changing whether the request is allowed. This lets adopters learn before introducing security-critical policy.

## 3. Product vision

Ostend aims to make a service interaction explainable in the following form:

> This authenticated principal attempted this operation under these declared and observed circumstances.

The desired future model is:

```text
Identity
Who or what is accountable?
        +
Capability
What resource or action is being exercised?
        +
Context
Why, when, how, and with what human involvement?
        =
Transparent request
```

Ostend does not replace authentication or authorization. It connects them to richer, explicit interaction context.

## 4. Product principles

### 4.1 Identity anchors accountability

Ostend shall preserve and associate existing service identity information rather than create a competing identity system in Iteration 1.

### 4.2 Capabilities describe possible effects

Ostend shall observe the resource and operation being requested without deciding whether that operation should be authorized.

### 4.3 Context describes current circumstances

Ostend shall begin with a narrow declaration of autonomous execution and expand only when additional context has clear semantics and practical value.

### 4.4 Missing information is unknown

The absence of an agent declaration shall mean **unspecified**, not human.

### 4.5 Claims and proof are different

Ostend shall distinguish a caller's voluntary declaration from independently verified evidence. Iteration 1 records a claim; it does not prove the claim.

### 4.6 Observation should not disrupt existing services

An adopter should be able to introduce Ostend without redesigning the existing service's authentication, authorization, or business logic.

### 4.7 Minimize sensitive collection

Ostend shall collect only the information needed to understand the interaction. It shall not log credentials, request bodies, prompts, agent memory, or sensitive service data by default.

## 5. Target users

### 5.1 API owner

An organization or team that operates an API and wants to understand when compliant autonomous agents use it.

### 5.2 Service operator

An engineer responsible for deploying, configuring, monitoring, and troubleshooting the proxy.

### 5.3 Agent developer

A developer building an autonomous client who wants to declare its mode of interaction consistently.

### 5.4 Downstream application developer

A developer maintaining an existing service who wants normalized agent-interaction metadata without implementing protocol parsing.

### 5.5 Trust, safety, or security researcher

A person evaluating agent participation patterns and the usefulness of identity-capability-context transparency.

## 6. User needs

### 6.1 API owner needs

The API owner needs to:

- Add agent disclosure support without replacing existing authentication.
- Distinguish declared-autonomous requests from unspecified requests.
- Associate a disclosure with the existing authenticated request.
- Observe adoption and behavior before applying new policy.
- Avoid classifying undeclared traffic as human.

### 6.2 Service operator needs

The service operator needs to:

- Deploy Ostend as a conventional containerized service.
- Configure exactly which upstream service receives traffic.
- Verify health and readiness.
- Receive structured, privacy-conscious logs.
- Diagnose malformed or unsupported declarations.
- Be confident that Ostend cannot become an arbitrary open proxy.

### 6.3 Agent developer needs

The agent developer needs to:

- Declare autonomous participation with one simple HTTP field.
- Use the protocol without an Ostend-specific SDK.
- Receive optional confirmation that a declaration was recognized.
- Understand precisely what “autonomous” means.
- Avoid disclosing prompts, model internals, or task content.

### 6.4 Downstream developer needs

The downstream developer needs to:

- Receive a small, normalized set of trusted internal fields.
- Avoid parsing the external protocol directly.
- Treat missing or invalid declarations as unspecified.
- Continue relying on the service's existing authorization system.

### 6.5 Researcher needs

The researcher needs to:

- Measure how often participating clients declare autonomy.
- Distinguish valid, missing, invalid, and unsupported declarations.
- Analyze attempted operations without collecting sensitive payloads.
- Avoid presenting voluntary declarations as verified facts.

## 7. Goals and non-goals

### 7.1 Iteration 1 goals

Ostend shall:

1. Give compliant clients a standard way to declare fully autonomous request generation and submission.
2. Parse and classify the declaration consistently.
3. Place that classification alongside existing identity and request-operation observations.
4. Forward requests without changing the upstream service's authorization behavior.
5. Produce normalized metadata and structured observation records.
6. Provide an implementation that can be deployed in front of an existing HTTP service.
7. Establish clear semantics that can support later experiments.

### 7.2 Iteration 1 non-goals

Ostend shall not:

- Detect agents that do not disclose themselves.
- Determine whether a caller is human.
- Verify that a declaration is truthful.
- Block autonomous, missing, invalid, or unsupported requests because of their classification.
- Prevent malicious or unintended behavior.
- Authenticate a model or agent runtime.
- Issue new user or agent credentials.
- Replace the upstream service's authorization system.
- Determine the agent's permitted capabilities.
- Prove human presence, observation, supervision, or approval.
- Represent delegation chains or task purpose.
- Inspect or evaluate prompts, reasoning, memory, or output quality.
- Provide a complete agent-trust framework in the first release.
- Provide end-to-end request confidentiality or integrity against a compromised Ostend deployment.
- Independently provide comprehensive denial-of-service protection.

## 8. Product model

### 8.1 Identity in Iteration 1

Ostend shall preserve the existing credential carried by the request and associate the disclosure observation with the request.

Ostend does not independently establish the authenticated principal in Iteration 1. The upstream service remains authoritative for authentication.

Where safe and available, logs may include a non-sensitive principal or client identifier supplied by trusted infrastructure. Credentials themselves must never be logged.

### 8.2 Capability in Iteration 1

Ostend shall observe the attempted HTTP operation through non-sensitive request metadata such as:

- HTTP method.
- Normalized route or path.
- Upstream service.
- Upstream response status.

These observations describe what the caller attempted. They do not establish that the caller possessed or was granted the capability. The upstream service makes that determination.

### 8.3 Context in Iteration 1

Ostend shall record whether the client provided a valid declaration that the request was autonomous.

The supported context classifications are:

- `valid`
- `missing`
- `invalid`
- `unsupported`

A valid Version 1 declaration produces the interaction mode `autonomous`. Every other classification produces `unspecified`.

## 9. User scenarios

### Scenario 1 — Compliant autonomous agent

**Actor:** Agent developer  
**Situation:** An autonomous scheduling agent calls an existing calendar API using a valid user-granted credential.  
**Action:** The client adds the Version 1 `Agent-Interaction` declaration.  
**Ostend behavior:** Ostend classifies the declaration as valid, records the request as autonomous, adds normalized internal metadata, and forwards the request.  
**Outcome:** The calendar service performs its existing authorization checks while operators can identify the request as declared autonomous.

### Scenario 2 — Existing client without disclosure support

**Actor:** Existing application  
**Situation:** An application sends a request without an `Agent-Interaction` field.  
**Ostend behavior:** Ostend classifies the request as missing or unspecified and forwards it normally.  
**Outcome:** Existing integrations continue to work. No claim is made that the request was human-generated.

### Scenario 3 — Malformed declaration

**Actor:** Agent developer  
**Situation:** A client sends an incorrectly formatted declaration.  
**Ostend behavior:** Ostend classifies it as invalid, records a bounded reason code, and forwards the request.  
**Outcome:** The client remains compatible with the service while the developer can identify and correct the protocol error.

### Scenario 4 — Unsupported future version

**Actor:** Agent developer  
**Situation:** A client sends a structurally valid declaration using a profile version not supported by the deployed proxy.  
**Ostend behavior:** Ostend classifies it as unsupported and forwards the request.  
**Outcome:** Version mismatch is observable without breaking the underlying API call.

### Scenario 5 — Downstream service consumes normalized metadata

**Actor:** Downstream application developer  
**Situation:** A service wants to include agent participation in its own audit events.  
**Action:** The service reads proxy-generated internal fields.  
**Outcome:** The service receives a consistent classification without parsing the external declaration.

### Scenario 6 — API owner evaluates adoption

**Actor:** API owner  
**Situation:** The owner wants to understand how much traffic is voluntarily declaring autonomous participation.  
**Action:** The owner analyzes structured Ostend events.  
**Outcome:** The owner can compare valid autonomous, unspecified, invalid, and unsupported request counts without examining request bodies.

### Scenario 7 — Existing authorization denies a request

**Actor:** Autonomous agent  
**Situation:** A compliant agent declares autonomy but lacks permission for the requested operation.  
**Ostend behavior:** Ostend forwards the request with normalized context.  
**Outcome:** The upstream service denies it using existing authorization. Ostend records the declaration and upstream status but does not make or override the authorization decision.

### Scenario 8 — False or omitted declaration

**Actor:** Noncompliant or malicious client  
**Situation:** A client omits or falsifies agent-interaction information.  
**Ostend behavior:** Ostend records only what can be observed: missing information or a syntactically valid declaration.  
**Outcome:** Ostend does not claim to have identified the true actor type. This is an accepted limitation of Iteration 1.

## 10. Feature scope

### 10.1 Must have

#### F-001 — Autonomous interaction declaration

Recognize the Version 1 HTTP field:

```http
Agent-Interaction: actor=agent, mode=autonomous, version=1
```

#### F-002 — Declaration classification

Classify every request as valid, missing, invalid, or unsupported.

#### F-003 — Transparent reverse proxy

Forward requests to one configured upstream origin while preserving existing authentication material and upstream responses.

#### F-004 — Reserved metadata sanitization

Remove caller-provided internal `Proxy-Agent-*` fields before generating normalized metadata.

#### F-005 — Normalized downstream metadata

Provide the upstream service with normalized declaration status, interaction mode, and profile version when known.

#### F-006 — Structured observation logs

Emit one structured event per completed request containing request identity, attempted operation, interaction classification, upstream outcome, and timing information without logging sensitive payloads.

#### F-007 — Health and readiness

Expose endpoints suitable for deployment health and readiness checks.

#### F-008 — Observation-only operation

Ensure that the agent declaration does not affect whether requests are forwarded.

#### F-009 — Containerized deployment

Provide an OCI-compatible container that can run on Railway and other container platforms.

#### F-010 — Protocol and integration tests

Verify classification, header sanitation, credential forwarding, body forwarding, response preservation, and non-blocking behavior.

### 10.2 Should have

#### F-011 — Optional acknowledgement

Allow a deployment to return a response field confirming that a valid declaration was recognized.

#### F-012 — Reason codes

Record bounded reason codes for invalid and unsupported declarations without logging the raw value.

#### F-013 — Request correlation

Associate proxy observations, upstream requests, and responses with an opaque request identifier.

#### F-014 — Privacy configuration

Allow path logging to be reduced or normalized when request paths contain sensitive identifiers.

### 10.3 Could have

- A minimal TypeScript client helper.
- A minimal Python client helper.
- OpenTelemetry trace attributes.
- A metrics endpoint with aggregate declaration counts.
- A local demonstration service and example autonomous client.
- A deployment template for Railway or Cloud Run.

### 10.4 Not in Iteration 1

- Dashboards or administrative user interface.
- Policy authoring or enforcement.
- Signed declarations.
- Workload attestation.
- Human-confirmation workflows.
- Model or framework registries.
- Task and purpose declarations.
- Capability tokens.
- Delegation exchange.
- Multi-upstream dynamic routing.
- Agent detection based on behavior.

## 11. User experience requirements

### 11.1 Agent-developer experience

A developer shall be able to participate by adding one HTTP request field. An SDK shall not be required.

The protocol documentation shall provide:

- The exact header syntax.
- The definition of autonomous.
- Examples of valid and invalid declarations.
- The meaning of acknowledgement.
- A statement that the declaration is voluntary and not independently verified.

### 11.2 API-owner experience

An API owner shall be able to:

1. Configure one upstream origin.
2. Deploy Ostend.
3. Direct API traffic through it.
4. Verify health.
5. Observe structured classifications.
6. Remove Ostend without changing client credentials or upstream authorization logic.

### 11.3 Downstream-developer experience

A downstream developer shall receive normalized internal fields whose meaning does not depend on parsing the external request.

Documentation shall warn that these fields are trusted only when clients cannot bypass Ostend and access the upstream directly.

### 11.4 Operational experience

Invalid configuration shall prevent readiness and produce a clear, non-sensitive startup error.

Protocol parsing failures shall not crash the proxy or block requests in observation mode.

## 12. Technical constraints

### 12.1 Existing authentication and authorization

- Ostend must coexist with the upstream service's existing authentication.
- Existing `Authorization` fields and applicable cookies must be forwarded unchanged.
- The upstream service remains authoritative for authorization.
- Ostend must not present a declaration as an authenticated agent identity.

### 12.2 HTTP compatibility

- The declaration shall use HTTP Structured Fields semantics.
- The proxy must correctly handle common HTTP methods, query strings, binary bodies, multipart bodies, empty bodies, and streaming responses.
- The proxy should avoid buffering complete bodies.
- Hop-by-hop HTTP fields must be handled according to HTTP semantics.

### 12.3 Routing

- The upstream origin must be configured by the operator.
- Clients must not select an arbitrary upstream.
- Iteration 1 supports one upstream origin per deployment.

### 12.4 Metadata trust boundary

- Caller-provided `Proxy-Agent-*` fields must be stripped.
- Only Ostend may generate normalized internal fields.
- Upstream network configuration should prevent direct public bypass when those fields are consumed as trusted metadata.

### 12.5 Privacy

By default, Ostend must not log:

- Credentials or cookies.
- Request or response bodies.
- Prompts or model output.
- Agent memory.
- Task descriptions.
- Raw health, financial, or other sensitive service data.
- Raw invalid declaration values.

### 12.6 Deployment

- The reference implementation will use TypeScript, Node.js, and Fastify.
- The product must be packaged as an OCI-compatible container.
- Railway is the initial deployment target.
- The implementation must not depend on Railway-specific application APIs.
- Google Cloud Run should remain a compatible future target.

### 12.7 Persistence

- Iteration 1 requires no application database.
- Observation events will be emitted as structured JSON to standard output.
- The deployment platform is responsible for collection and retention.

### 12.8 Failure handling

- Missing, invalid, and unsupported declarations must remain non-blocking.
- Upstream failures must return appropriate gateway errors.
- Error responses must not reveal credentials, stack traces, or private network details.

### 12.9 Intermediary trust and availability

- Iteration 1 treats Ostend and its deployment platform as trusted parts of the request path.
- Ostend terminates the client TLS connection and establishes a separate TLS connection to the upstream service.
- Public client-to-Ostend and Ostend-to-upstream traffic must use HTTPS.
- Ostend must validate the upstream service's certificate and hostname.
- Production configuration must not allow upstream TLS certificate validation to be disabled.
- The proof of concept should use test credentials or credentials that are short-lived and narrowly scoped.
- The proof of concept should not carry sensitive production traffic.
- Iteration 1 does not provide end-to-end integrity against a compromised Ostend instance because the proxy can observe or modify HTTP requests by design.
- Iteration 1 relies on Railway's platform controls for baseline traffic handling, scaling, and availability protection. Comprehensive denial-of-service mitigation is outside its scope.

## 13. Product requirements

### PR-001 — Clear declaration semantics

Ostend must publish a precise definition of autonomous request generation and distinguish it from human initiation of a broader task.

### PR-002 — Conservative classification

Ostend must never infer human involvement from missing agent metadata.

### PR-003 — Claim transparency

User-facing documentation and machine-generated metadata must describe the classification as a declaration or observation, not proof.

### PR-004 — Compatibility

Introducing Ostend must not require the existing service to replace credentials, permissions, or business logic.

### PR-005 — Observable identity-capability-context relationship

For each completed request, Ostend must be capable of associating:

- The request identifier and any safely available authenticated-principal reference.
- The attempted method and resource.
- The agent-interaction declaration status and mode.
- The upstream outcome.

### PR-006 — Data minimization

Ostend must provide useful request transparency without inspecting or retaining application payloads.

### PR-007 — Safe adoption

The first release must default to observation-only behavior and make enforcement unavailable or clearly unsupported.

### PR-008 — Portability

The reference implementation must run locally and on a standard container platform.

### PR-009 — Explicit trust boundary

Product documentation must state that Iteration 1 is a trusted, TLS-terminating intermediary and must distinguish transport protection on each proxy connection from end-to-end request integrity.

### PR-010 — Future production deployment options

A production version of Ostend should support deployment models and security integrations that reduce intermediary and availability risk, such as customer-managed deployment, private-network gateways, upstream sidecars or middleware, cryptographically signed requests, sender-constrained credentials, rate limiting, and managed edge denial-of-service protection.

## 14. Success measures

Iteration 1 will be successful when:

### 14.1 Functional success

- A compliant client can declare an autonomous request using one HTTP field.
- Ostend classifies valid, missing, invalid, and unsupported declarations correctly.
- Existing authenticated requests continue to reach the upstream.
- Upstream authorization outcomes are preserved.
- Normalized metadata and observation events are generated reliably.

### 14.2 Adoption success

During a pilot:

- At least one autonomous client integrates without an Ostend-specific SDK.
- At least one existing API operates behind Ostend without authentication or authorization changes.
- Operators can locate and interpret autonomous request observations.

### 14.3 Quality success

- Required automated tests pass.
- No credentials or bodies appear in default logs during test verification.
- Caller-supplied internal metadata cannot override Ostend-generated fields.
- The proxy cannot be used as an arbitrary open proxy.
- Measured proxy application processing overhead remains within the SRS target under expected pilot load.

### 14.4 Learning success

The pilot should produce evidence addressing:

- Whether developers understand and apply the definition of autonomous consistently.
- Whether the declaration format is sufficient for common HTTP clients.
- Whether normalized identity, operation, and context observations are useful to API owners.
- Which additional context users request next.
- Whether optional acknowledgement materially improves developer experience.

## 15. Risks and mitigations

| Risk | Consequence | Mitigation |
|---|---|---|
| Users interpret declarations as verified facts | False confidence | Consistently label them as voluntary declarations |
| Missing declarations are treated as human | Misclassification | Require `unspecified` semantics |
| The product scope expands into enforcement too soon | Unclear and unsafe policy | Keep Iteration 1 observation-only |
| Logs expose sensitive data | Privacy or security harm | Default to metadata-only structured logging |
| Direct upstream access permits forged internal fields | Misleading observations | Strip reserved fields and document the network trust boundary |
| Proxy changes API behavior | Adoption failure | Preserve credentials, methods, bodies, statuses, and streaming |
| Header semantics fragment | Poor interoperability | Publish one strict Version 1 profile |
| Ostend becomes an open proxy | Infrastructure abuse | Use one operator-configured upstream |
| Voluntary adoption produces incomplete data | Biased measurements | Treat results as declared participation, not total agent traffic |
| A compromised Ostend deployment reads or changes requests | Credential theft or loss of request integrity | Treat Ostend as trusted in the proof of concept, use TLS on both connections and narrowly scoped test credentials, and document that end-to-end integrity is not provided |
| Traffic overwhelms the public proxy | Reduced availability or increased cost | Rely on Railway's baseline platform controls for the proof of concept, apply reasonable resource limits, and require stronger edge and rate-limiting options for a production product |

## 16. Dependencies

Iteration 1 depends on:

- A reachable HTTP or HTTPS upstream service.
- A deployment environment capable of running the container.
- An RFC 9651-compatible Structured Fields implementation.
- Structured log collection by the deployment platform.
- Client willingness to send the declaration.

It does not depend on:

- A new identity provider.
- A new OAuth server.
- A database.
- WebAuthn.
- A model provider.
- A specific agent framework.

## 17. Release plan

### Phase 1 — Local prototype

- Implement protocol parsing and classification.
- Implement fixed-upstream proxying.
- Add internal-field sanitization.
- Add structured observations.
- Build a mock upstream and automated tests.

### Phase 2 — Hosted pilot

- Package as a container.
- Deploy to Railway.
- Configure health and readiness checks.
- Require HTTPS on both proxy connections and validate the upstream certificate and hostname.
- Use test or narrowly scoped, short-lived credentials.
- Avoid routing sensitive production traffic through the proof-of-concept deployment.
- Integrate one compliant autonomous client.
- Place one test API behind Ostend.

### Phase 3 — Evaluation

- Review declaration consistency.
- Review operational logs and privacy behavior.
- Measure compatibility and processing overhead.
- Gather feedback from agent developers and API owners.
- Decide whether to revise Version 1 or add another contextual claim.

## 18. Future direction

Future releases may make additional aspects of identity, capability, and context explicit:

### Identity

- Agent execution identity.
- Responsible organization.
- Delegating user or service.
- Workload or runtime attestation.

### Capability

- Structured requested actions.
- Resource and data boundaries.
- Short-lived capability grants.
- Delegation attenuation.

### Context

- Task purpose.
- Human supervision.
- Transaction-specific human confirmation.
- Time and usage limits.
- Delegation depth.
- Data-retention and onward-disclosure constraints.

### Deployment and transport security

- Customer-managed and private-network deployments.
- Sidecar, service-mesh, gateway-plugin, and application-middleware integrations.
- End-to-end HTTP message signatures verified by the upstream service.
- Sender-constrained credentials.
- Workload identity and mutual TLS between trusted services.
- Configurable rate limiting, quotas, and request-size limits.
- Integration with managed edge denial-of-service protection.

These additions should be introduced as separately defined claims with clear sources of evidence. They must not be treated as verified merely because a client includes them.

## 19. Open product questions

The following questions are intentionally deferred until Iteration 1 produces practical feedback:

1. Should Ostend expose an optional well-known discovery document?
2. Should acknowledgement be enabled by default?
3. Is a TypeScript or Python client helper useful enough to maintain?
4. How should routes containing sensitive identifiers be normalized?
5. Which safely available identity reference is most useful in observations?
6. Should a later version distinguish human-supervised from transaction-confirmed interactions?
7. When should declarations become cryptographically bound to a request?
8. What evidence should support future identity and context claims?
9. Should Ostend remain a proxy, or should the protocol also have gateway and middleware implementations?
10. Which production deployment models should provide end-to-end integrity without preventing Ostend from observing required disclosure metadata?
11. Which denial-of-service controls belong in Ostend itself, and which should remain the responsibility of the deployment platform or edge provider?

None of these questions blocks Iteration 1.

## 20. Relationship to the SRS

This PRD defines why Ostend should exist, whom it serves, what user problem it addresses, and which features belong in the first product iteration.

The accompanying Software Requirements Specification defines the detailed protocol behavior, functional requirements, non-functional requirements, security boundaries, test requirements, and acceptance criteria for implementation.

Where the documents appear to conflict, the narrower Iteration 1 behavior in the SRS should govern implementation until the product and engineering requirements are reconciled explicitly.

## Appendix A — Core product statement

## Appendix B — Iteration 1 promise

For a compliant request, Ostend can say:

> An authenticated request attempted this operation and declared that it was selected, constructed, and submitted autonomously.

Ostend cannot yet say:

> The caller was proven to be an agent, its declaration was truthful, or the request was safe and properly authorized.
